Owner & vendor onboarding
[C] Registration creates a pending application. It does not grant duty access until the relevant Admin approval is
complete.
Owner Driver: self-registration in Driver App
1. Verify the driver's own mobile number by OTP.
2. Submit driving licence details/image and a selfie.
3. Register the attached vehicle with RC, Insurance, FC, Permit and a front vehicle photo.
4. Admin reviews the driver and the vehicle. Rejected or incomplete submissions show a reason and allow
correction.
5. After both are approved, activate the Owner Driver experience and eligible duty access.

Same approval process

The original business proposal was call + invitation only. The combined in-app application and assisted-link route is a

04 / FUNCTIONAL SPECIFICATION
Driver identity & fleet management
[C] Vendors can add multiple Drivers and Vehicles. Removing/deleting or changing account relationships
remains under Admin control.
Action
Required behaviour
Add Driver
Create an invitation/pending profile using the driver's own mobile number and licence
details. System generates Driver ID.
Activate Vendor Driver
Driver verifies that number by OTP in the same Driver App and completes required
identity/selfie verification. Admin approval grants the limited Vendor Driver role.
Existing Driver ID
Match the existing identity. Do not create a second account or silently move an Owner Driver
into a Vendor. Request Admin review/linking.
Add Vehicle
Create Vehicle ID with registration number, vehicle category and RC, Insurance, FC, Permit
and front photo.
Assign Trip
Select an approved, available Driver and an approved, available Vehicle. Both must belong to
the Vendor's authorized fleet relationship.
Remove / transfer
Vendor may request a change. Admin approves deactivation, unlinking or transfer; retain
historical trip and financial records.
Driver and vehicle are separate resources
A driver is not permanently the same entity as a vehicle. A trip stores both assigned_driver_id and
assigned_vehicle_id. This permits a Vendor to select another approved vehicle without creating a new Driver ID.
[R] Check schedule overlap for the Driver and Vehicle independently. A running trip must not block every future
booking; it blocks assignments whose time window and travel buffer conflict. Buffer rules remain configurable
[D06].
No automatic promotion
Removing a Vendor association must never turn a Vendor Driver into an Owner Driver. Show an
inactive/unassigned state until Admin approves a new Vendor link or an Owner Driver application.
[R] Preserve account history during approved role changes. Do not transfer settled earnings or historical wallet ownership when
a driver changes employer. Pending documentation or unapproved replacement vehicles cannot be used to bypass verification.

Booking approval & dispatch
[C] Customer submits booking to Admin. Only an approved booking enters the duty distribution process. Admin
can see the booking throughout.
Server elapsed time
Eligible offer audience
0:00 to before 2:00
Approved high-rated Owner Drivers first. Exact rating threshold / review count is D01.
At 2:00 (120 seconds)
Other eligible approved Owner Drivers are added. The initial group remains eligible.
At 3:00 (180 seconds)
Approved eligible Vendors are added. Owner Drivers remain eligible.
After any successful claim
Stop further release for that booking and remove it from other Open Duty lists.
Timing interpretation: Vendor access begins after three complete minutes, not at the start of the third minute. Use Admin
approval / dispatch start as time zero; confirm this interpretation with D01.
ADMIN APPROVES
Server records the dispatch start time.
OWNER DRIVER WINS
Accept + attach the approved vehicle.
VENDOR WINS
Reserve to Vendor; assign Driver + Vehicle.
ONE BOOKING - ONE SUCCESSFUL CLAIM - ONE SETTLEMENT OWNER
Claim and assignment contract [R]
1. Apply eligibility by role, approval, requested vehicle category, service area and the booking time window. No
Vendor Driver belongs to this offer audience.
2. Make claim acceptance atomic on the server. Concurrent Owner Driver/Vendor attempts produce exactly one
winner; the others receive Already Assigned.
3. For a Vendor winner, reserve the booking to that Vendor before assigning Driver + Vehicle. The assignment
deadline and release policy are still D06.
4. Notify the customer when driver/vehicle details are assigned. If no eligible partner claims the booking, keep it
visible to Admin for intervention rather than silently completing or cancelling it.
[R] Timers use server time and survive app closure. Cancel obsolete offer jobs after claim/cancellation; do not replay an old
dispatch wave into an assigned trip.

06 / FUNCTIONAL SPECIFICATION
Trip lifecycle
[C] Both driver types use the same trip operation sequence. The Vendor Driver only operates a trip already
assigned to that driver.
State / action
Gate and result
ASSIGNED / UPCOMING
Show pickup, drop, date/time and assigned vehicle. Future trips appear in My Trips.
Start availability uses the configured start window [D06].
Start for Pickup
Open verification capture for this assigned trip. Capture live driver selfie and live
front vehicle photo; no gallery selector.
READY TO DEPART / EN_ROUTE
After required evidence is accepted, allow Navigate to Pickup and show the next trip
action.
Reached Pickup
Server validates distance from pickup coordinates before accepting the action.
Working radius is 3 km; final confirmation is D02.
BOARDING OTP
Require the customer's trip-specific OTP. Reached Pickup alone does not start the
passenger journey.
IN_PROGRESS
Enable trip operation / navigation. Do not allow another trip to start for the same
Driver or Vehicle.
End Trip / submit Trip KM
Driver enters total billable trip kilometres only. Server validates the entry and
calculates the final fare from the stored rate rules.
COMPLETED / invoice ready
Driver and Customer see the same customer fare breakdown, verified payments and
amount still to collect.
Payment / settlement
Confirmed receipts update payment status. Collection confirmation and partner
settlement are separate from Trip Completed.
Independent states
Trip status, payment status and settlement status are separate. A completed trip can be awaiting payment; an
online payment can be received before the trip; a paid trip can be awaiting partner payout.
[R] Reject out-of-sequence actions, another driver's trip actions and duplicate terminal transitions. Admin exceptions require an
explicit reason and an audit record. Cancellation, no-show and disputed-distance charging are not defined business tariffs [D10].

Calculation contract
extra_km = max(actual_trip_km - included_km, 0)
extra_net_fare = extra_km × stored_extra_km_rate
final_total = quoted_gross_fare + extra_net_fare + extra_gst
The formula assumes the extra-km rate excludes GST and the package quote already includes GST. A
tax-inclusive extra rate must be split into base and tax, not taxed again.
Declared example assumptions [D04 / D05]
1. The ₹400 bata is included in the taxable base here. Confirm this tax treatment and tax responsibility with the
accountant.
2. Commission is only on the running fare excluding trip GST; the bata is not commissionable under the stated
rule.
3. The fixed quoted package is retained below included km in this draft calculation. Confirm the below-package
minimum and billable-distance definition before production.
[R] Use decimal/paise arithmetic and a documented two-decimal rounding method. Do not round each kilometre or use binary
float values as the accounting source of truth.

Wallet & small payouts
[C] The business requested payments below ₹300 to go directly into the appropriate Driver or Vendor wallet. The
interpretation below is still D07.
Proposed threshold interpretation [D07]
Apply the rule to the positive net amount Nesam owes the partner after collection, commission and trip GST
adjustments. If 0 < net payable < ₹300, retain/credit it in the correct wallet automatically. Confirm the basis, exactly
₹300 and amounts above ₹300 before enabling routing.
₹1,000 advance: transparent ledger example
Partner ledger entry
Effect
Customer payment received by Nesam
+₹1,000.00
Nesam running-fare commission
-₹465.00
Trip GST held by Nesam
-₹252.50
Net partner wallet increase
+₹282.50
The +₹282.50 is the result of those entries. Do not add another +₹282.50 entry on top of them. If the advance
was already credited earlier, reference that original entry rather than posting the advance twice.
Posting rules [R]
1. Attach every credit/debit to the booking and settlement owner. Use unique event references so retries cannot
post the same receipt, fee or GST twice.
2. A wallet credit must not also trigger a duplicate direct bank payout for the same amount.
3. A later approved wallet withdrawal reduces that wallet balance and has its own payout reference. Wallet credit
does not mean the money can never be withdrawn.
4. For Vendor bookings, use only the Vendor wallet. The employee Driver receives no separate credit/debit for
the same partner settlement.
5. Store reversals as new linked entries. Do not edit or delete historical ledger amounts after posting.
Separate receipt, entitlement and transfer
Maintain the earned partner entitlement even when the payout channel is not decided. Exactly ₹300, larger
payouts, withdrawal timing, minimum balances and negative-balance duty rules remain business decisions [D07 /
D08].

13 / FUNCTIONAL SPECIFICATION
Server controls & operational handling
[R] The following controls make the requested behaviour reliable across multiple apps, repeated taps, network
retries and account changes.
Control
Required result
Role + ownership checks
Owner Driver sees own permitted records. Vendor sees its authorized fleet/bookings.
Vendor Driver sees only own assigned trips. Validate every request [S1].
Approval gate
Pending/suspended accounts and unapproved resources cannot gain marketplace or trip
privileges by changing client fields.
Atomic booking claim
Exactly one successful booking claimant. Concurrent losers receive the current assignment
state.
State transition validation
Reject invalid or stale trip actions. Scope customer boarding OTP to the correct trip and do
not reuse account-login OTP.
Payment verification
Trust verified payment events/confirmed receipts, not a client-supplied Paid flag.
Deduplicate provider events.
Ledger idempotency
One posting per financial event. Repeated End Trip / callback retries cannot create extra
deductions or payouts.
Role or Vendor change
Server permissions change when Admin updates the account. An old app screen/session
must not preserve revoked access.
Resource conflict
Recheck Driver and Vehicle availability at assignment/start. A concurrent assignment must
not bypass overlap checks.
Documents / evidence
Restrict document access and evidence ownership. Expired required documents block new
assignments under the configured policy.
Offline / failed request
Show the last confirmed state plus a retry message. Do not pretend a booking was
accepted, OTP verified or payment received.
Admin exceptions remain traceable
Provide review queues for unassigned bookings, missing assignments, document corrections, distance disputes
and unsettled payments. Cancellation, reassignment, payment correction and wallet reversal require a recorded
actor/reason and consistent customer/partner updates.
Do not invent cancellation charges, toll/parking rules, automatic no-show charges, penalties or automatic overdraft blocks. Route
undefined cases to Admin until the relevant policy is approved [D08-D10].
